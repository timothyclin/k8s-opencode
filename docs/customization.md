# K8s-OpenCode Customization Guide

How to customize the OpenCode configuration generated by this Helm chart — for
both single-user and multi-user deployments.

---

## Overview

Every OpenCode pod launched by this chart gets a generated `opencode.jsonc`
mounted at `/root/.config/opencode/opencode.jsonc`. The chart builds this file
from your `values.yaml` using the `ok8s.opencodeConfig` (single-user) or
`ok8s.opencodeUserConfig` (multi-user) named templates in `_helpers.tpl`.

The generated config controls:

- **Plugins** — npm packages loaded by OpenCode at startup (Oh-My-OpenCode,
  design tools, etc.)
- **Skills** — reusable prompt templates and tool configurations
- **MCP servers** — both remote HTTP endpoints and laptop servers via Tailscale

A second file, `oh-my-opencode.jsonc`, configures the Oh-My-OpenCode plugin
itself (Sisyphus task runner, agent models, skill lists). In multi-user mode,
each user gets their own copy of both files.

**The files are read-only from inside the pod.** They're sourced from a
ConfigMap and mounted as a volume — editing them directly won't persist. All
changes go through `values.yaml` + `helm upgrade`. See [Quick Start](../README.md#quick-start) for install commands.

To inspect the generated config at any time:

```bash
kubectl exec -it <pod-name> -- cat /root/.config/opencode/opencode.jsonc
```

## Plugins

Plugins are npm packages that extend OpenCode's capabilities. They load at
startup and can add new tools, agents, and UI features.

### Default Plugins

When `plugins.enabled: true` (the default), two plugins are always installed:

| Plugin | Purpose |
|--------|---------|
| `oh-my-opencode@latest` | Multi-agent orchestration, Sisyphus task runner |
| `@tarquinen/opencode-dcp@latest` | Design system and component tools |

### Disable Default Plugins

To strip all plugins from the generated config:

```yaml
plugins:
  enabled: false
```

This removes the `"plugin"` key from `opencode.jsonc` entirely. Useful if
you're running a minimal, plugins-free setup.

### Add Extra npm Plugins

To add plugins on top of the defaults, list them under `plugins.npm`. Each
entry is an npm package specifier (name, name@version, @scope/name, etc.):

```yaml
plugins:
  enabled: true
  npm:
    - "my-custom-plugin@latest"
    - "@my-org/opencode-tools@2.1.0"
```

The extra plugins are appended after the two defaults in the generated config.

### Multi-User Mode

Plugin configuration applies to all users — there's no per-user plugin list.
`plugins.enabled` and `plugins.npm` are global. Every user's `opencode.jsonc`
gets the same plugin array.

## Skills

Skills are reusable prompt templates and tool configurations loaded by
Oh-My-OpenCode. They can be npm packages or inline config objects.

### npm Skills

npm skills are published packages that contain skill definitions. Add them
under `skills.npm` (single-user) or `sharedSkills.npm` (multi-user shared):

```yaml
# Single-user or per-user
skills:
  npm:
    - name: "@my-org/skills@latest"
    - name: "@my-org/coding-standards@1.0.0"
```

```yaml
# Multi-user: shared across all users
sharedSkills:
  npm:
    - name: "@my-org/company-skills@latest"
```

### Config Skills

Config skills are inline skill definitions — useful for project-specific rules
or custom agent personas you don't want to publish as an npm package. Each
entry needs a `name` and a `source` (URL or path to a Markdown file):

```yaml
# Single-user or per-user
skills:
  config:
    - name: "typescript-rules"
      source: "https://raw.githubusercontent.com/my-org/rules/main/typescript.md"
    - name: "code-review-checklist"
      source: "https://example.com/checklist.md"
```

```yaml
# Multi-user: shared across all users
sharedSkills:
  config:
    - name: "company-guidelines"
      source: "https://internal.example.com/guidelines.md"
```

### Shared vs. Per-User Skills (Multi-User Mode)

In multi-user mode, the chart merges shared and per-user skills into a single
`"skills"` block in each user's config. The order is always shared first, then
user-specific:

```yaml
sharedSkills:
  npm:
    - name: "@company/shared@latest"   # loaded for everyone
  config:
    - name: "shared-rules"
      source: "https://example.com/shared.md"

users:
  - name: alice
    skills:
      npm:
        - name: "@alice/personal@latest"  # only loaded for alice
      config:
        - name: "alice-rules"
          source: "https://example.com/alice.md"
```

Alice's generated config will contain: `[@company/shared@latest, @alice/personal@latest]`.

### Single-User Example

A complete skills block for single-user mode:

```yaml
skills:
  npm:
    - name: "@my-org/engineering-skills@latest"
  config:
    - name: "project-conventions"
      source: "https://raw.githubusercontent.com/my-org/repo/main/CONVENTIONS.md"
```

## MCP Servers

MCP (Model Context Protocol) servers expose tools to OpenCode agents. The chart
supports two kinds: remote servers reachable over HTTP, and laptop servers
accessible via Tailscale.

### Remote MCP Servers

Remote servers are accessed directly over HTTP. They must be reachable from
inside the cluster (internal services, public URLs, etc.):

```yaml
mcp:
  remote:
    - name: context7
      url: https://mcp.context7.com/mcp
      enabled: true
    - name: internal-tools
      url: http://tools-service.internal-namespace.svc.cluster.local:8080/mcp
      enabled: true
```

Optional fields:

```yaml
mcp:
  remote:
    - name: authenticated-server
      url: https://api.example.com/mcp
      enabled: true
      headers:
        Authorization: "Bearer my-token"
      oauth:
        clientId: "my-client-id"
        clientSecret: "my-client-secret"
```

### Laptop MCP Servers (via Tailscale)

Laptop servers run on your local machine. The chart creates a Tailscale egress
proxy for each one so the cluster can reach your laptop over WireGuard:

```yaml
mcp:
  laptopServers:
    - name: playwright
      tailscaleIP: "100.x.x.x"   # run: tailscale ip -4
      port: 3000
    - name: browser-tools
      tailscaleIP: "100.x.x.x"
      port: 3001
```

If your laptop uses MagicDNS instead of a static IP:

```yaml
mcp:
  laptopServers:
    - name: playwright
      tailscaleFqdn: "my-laptop.lynx-beta.ts.net"
      port: 3000
```

Each entry creates a Kubernetes ExternalName Service named
`<release>-egress-<name>`. The generated `opencode.jsonc` references these
services by their cluster-internal DNS names — the Tailscale operator handles
the WireGuard tunneling transparently.

> **Prerequisite**: The Tailscale operator must be installed and the
> `ProxyClass` resource must be deployed. See `README.md` for Tailscale setup.

### Shared MCP Servers (Multi-User Mode)

To share MCP servers across all users, use `sharedMcp`:

```yaml
sharedMcp:
  - name: context7
    url: https://mcp.context7.com/mcp
    enabled: true
  - name: shared-internal
    url: http://tools.internal.svc.cluster.local/mcp
    enabled: true
```

Users can also add their own MCP servers that don't appear for other users:

```yaml
users:
  - name: alice
    mcp:
      remote:
        - name: alice-custom
          url: https://alice.example.com/mcp
          enabled: true
      laptopServers:
        - name: playwright
          tailscaleIP: "100.x.x.x"
          port: 3000
```

In multi-user mode, each user's generated config merges shared servers first,
then user-specific servers.

## Environment Variables

### Provider API Keys

API keys are injected as environment variables from a Kubernetes Secret. Set
them in `values.yaml` under `providers`:

```yaml
providers:
  anthropic:
    enabled: true
    apiKey: "sk-ant-..."
  openai:
    enabled: true
    apiKey: "sk-..."
  google:
    enabled: true
    apiKey: "AIza..."
    projectId: "my-gcp-project"   # for Vertex AI
```

Disabled providers don't inject any env vars.

In multi-user mode, each user has their own provider config under their user
entry — separate secrets, separate env vars:

```yaml
users:
  - name: alice
    providers:
      anthropic:
        enabled: true
        apiKey: "sk-ant-alice-key"
  - name: bob
    providers:
      openai:
        enabled: true
        apiKey: "sk-bob-key"
```

### OPENCODE_ENABLE_EXA

`OPENCODE_ENABLE_EXA=1` is always injected into every pod, enabling web search
support via the Exa search API. This is unconditional — you don't configure it.

**API key is optional** — if not provided, Exa search silently fails but the
pod continues running. For production web search, add the key via `extraEnv`:

```yaml
extraEnv:
  - name: EXA_API_KEY
    value: "exa-..."
```

Or use the `/connect` command after logging in to authenticate with Exa.

### Extra Environment Variables

For any env var not covered by the chart's built-in fields, use `extraEnv`:

```yaml
extraEnv:
  - name: MY_CUSTOM_VAR
    value: "my-value"
  - name: EXA_API_KEY
    value: "exa-..."
  - name: SOME_FEATURE_FLAG
    value: "true"
```

You can also reference existing Secrets:

```yaml
extraEnv:
  - name: EXA_API_KEY
    valueFrom:
      secretKeyRef:
        name: my-secrets
        key: exa-api-key
```

`extraEnv` applies to all pods in single-user mode. In multi-user mode, it
applies to every user's pod — there's no per-user `extraEnv`.

## Common Customizations

### Add a Public MCP Server

```yaml
mcp:
  remote:
    - name: context7
      url: https://mcp.context7.com/mcp
      enabled: true
```

### Connect to a Laptop MCP Server

1. Find your laptop's Tailscale IP: `tailscale ip -4`
2. Start your MCP server on the laptop (e.g., `npx @playwright/mcp-server`)
3. Add to `values.yaml`:

```yaml
mcp:
  laptopServers:
    - name: playwright
      tailscaleIP: "100.x.x.x"
      port: 3000
```

4. Upgrade: `helm upgrade ok8s oci://ghcr.io/timothyclin/k8s-opencode/chart/ok8s -n opencode -f values.yaml`

### Add Team-Wide Skills (Multi-User)

```yaml
sharedSkills:
  npm:
    - name: "@my-company/engineering-skills@latest"
  config:
    - name: "code-review-guidelines"
      source: "https://github.com/my-company/standards/raw/main/code-review.md"
```

### Inject a Secrets Manager Key

This approach supplies API keys at deploy time:

```yaml
extraEnv:
  - name: EXA_API_KEY
    valueFrom:
      secretKeyRef:
        name: opencode-extra-secrets
        key: exa-api-key
```

**Alternative: Use /connect** — After logging in, run `/connect` in the terminal
to authenticate with providers (including Exa) without pre-configuring secrets.

### Disable Plugins for a Minimal Setup

```yaml
plugins:
  enabled: false
```

This produces an `opencode.jsonc` with no `"plugin"` key — OpenCode loads no
plugins and runs as a bare agent.

### Add an Extra Plugin Without Changing Defaults

```yaml
plugins:
  enabled: true   # keeps oh-my-opencode and opencode-dcp
  npm:
    - "my-experimental-plugin@0.1.0"
```

### Inject Arbitrary OpenCode Config

For config options not exposed as dedicated values, use `opencode.extraConfig`.
This is a JSON string merged into the generated config:

```yaml
opencode:
  extraConfig: |
    "autoshare": true,
    "theme": "dark"
```

> This is an advanced escape hatch. The string is injected verbatim into the
> JSON object, so it must be valid JSON key-value pairs with a trailing comma
> if more keys follow. Malformed JSON here will break the config file.

## AI Auto-Configuration

If you're an AI agent configuring this chart on behalf of a user, these are
the key patterns to follow.

### Locating Values to Change

All configurable options live in `chart/values.yaml`. Every key has a
`# -- description` comment above it (helm-docs format). The generated config
logic is in `chart/templates/_helpers.tpl` — look at `ok8s.opencodeConfig`
(single-user) and `ok8s.opencodeUserConfig` (multi-user) to understand exactly
what values map to what JSON output.

### Single-User Configuration Checklist

1. Provider key under `providers.anthropic` (or `openai` / `google`)
2. Server password under `serverPassword`
3. MCP servers under `mcp.remote` or `mcp.laptopServers`
4. Extra skills under `skills.npm` or `skills.config`
5. Any extra env vars under `extraEnv`
6. Apply: `helm upgrade ok8s oci://ghcr.io/timothyclin/k8s-opencode/chart/ok8s -n opencode -f values.yaml`

### Multi-User Configuration Checklist

1. Set `mode: "multi"`
2. Add users under `users[]` with `name`, `password`, and `providers`
3. Add `email` to each user if OIDC auth is enabled
4. Shared MCP servers under `sharedMcp`
5. Shared skills under `sharedSkills.npm` / `sharedSkills.config`
6. Per-user MCP servers under `users[].mcp.remote` / `users[].mcp.laptopServers`
7. Per-user skills under `users[].skills.npm` / `users[].skills.config`
8. Apply: `helm upgrade ok8s oci://ghcr.io/timothyclin/k8s-opencode/chart/ok8s -n opencode -f values.yaml`

### Verifying the Generated Config

After upgrading, confirm the config was generated correctly:

```bash
# Single-user
kubectl exec -it <pod-name> -- cat /root/.config/opencode/opencode.jsonc

# Multi-user (replace alice with actual username)
kubectl exec -it <release>-alice-0 -- cat /root/.config/opencode/opencode.jsonc
```

Or preview without deploying using `helm template`:

```bash
helm template ok8s ./chart -n opencode -f values.yaml | grep -A 30 "opencode.jsonc"
```

### What Not to Invent

Don't add config keys that don't exist in `values.yaml`. The chart is strict
about what it generates — unknown keys in `values.yaml` are silently ignored
by Helm but won't appear in the output. If a config option you need isn't
exposed, use `opencode.extraConfig` as the escape hatch or check if there's a
template in `_helpers.tpl` that handles it.
